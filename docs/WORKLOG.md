# 开发日志 / Worklog

本日志记录每个开发阶段不仅“做了什么”，还必须记录它对学校业务可能产生的影响、带来的收益以及仍然存在的风险。

每次完成一个可独立验收的开发段落后更新本文件。

---

## 2026-09-16 — Phase 1A：Django 工程底座

### 做了什么

- 建立 `feat/phase-01-foundation` 开发分支。
- 以 Django 5.2 LTS 为核心建立后端工程。
- 采用 PostgreSQL 作为标准数据库。
- 建立 Development / Test / Staging / Production 四套配置入口。
- 默认语言设为简体中文，默认时区设为 `Asia/Shanghai`。
- 建立 `core / schools / accounts / students / academics / reports / events / notifications / audit` 模块边界，但暂不提前实现业务模型。
- 增加中文首页、基础错误页和 `/health/` 健康检查。
- 增加最小自动化测试和 GitHub Actions 检查流程。
- 因仓库此前没有 CI，先将测试工作流引导文件加入 `main`，再由本分支重新触发 Pull Request 检查。
- 开发环境继续禁止任何真实学生数据。

### 对业务可能产生的影响

本阶段不会直接改变教师、学生或家长的工作流程，它的价值是建立后续所有业务功能共同依赖的稳定底座。

最重要的业务意义是：以后学习报告、请假、考勤、作业等能力不需要各自重复建设账号、权限、配置、日志和部署结构，避免平台从一开始就形成彼此割裂的“小系统”。

### 带来的好处

1. **降低未来改造成本**：环境和模块边界先统一，后续功能可以在同一工程规范下自然扩展。
2. **降低上线风险**：测试、预发布、生产配置从第一天分离，减少“开发环境能跑，生产环境混乱”的概率。
3. **减少供应商锁定**：Django + PostgreSQL + Linux 路线可迁移，不依赖单一云平台。
4. **中国场景默认正确**：中文和上海时区不是后期补丁，而是基础默认值。
5. **尽早形成质量门槛**：每次 Pull Request 可自动进行 Django 检查、数据库迁移和测试。
6. **为多学校扩展留出空间**：`schools` 等核心模块已经建立边界，但没有提前引入复杂多租户基础设施。

### 当前遗留风险

1. **数据库尚未建立业务模型**：当前 PostgreSQL 只承担 Django 基础表，School / Student 等将在下一阶段建立。
2. **生产安全仅有最低骨架**：HTTPS 终止、反向代理、安全头完整配置、密钥管理、备份和监控仍属于后续阶段。
3. **健康检查目前是浅检查**：`/health/` 只证明 Web 应用能响应，还没有检查数据库等依赖状态。
4. **依赖仍需持续安全更新**：Django 采用 5.2 LTS 分支并允许安全补丁升级，但后续仍需建立依赖升级机制。
5. **尚未证明模块边界完全正确**：这些边界是基于当前产品哲学设计的起点，后续应根据真实业务闭环验证，而不是为了保持目录漂亮而拒绝必要调整。

## 2026-09-16 — Phase 1B：首次机器验收与 CI 修正

### 做了什么

- 建立并实际触发 GitHub Actions 的 PostgreSQL 测试环境。
- 首次 CI 在依赖安装阶段失败：`Django>=5.2.18` 当时未能从 PyPI 获取。
- 根据 CI 的真实可安装结果，将 Django 5.2 LTS 下限调整为 `5.2.17`，并继续限制 `<5.3`，避免自动跨入非目标主版本。
- 将 `actions/checkout` 与 `actions/setup-python` 更新到 v7，消除旧 Node 20 runtime 的弃用风险。
- 第二轮 CI 完整通过：依赖安装、`manage.py check`、PostgreSQL migration、自动化测试全部成功。

### 对业务可能产生的影响

这一步仍然不直接改变学校端功能，但它建立了一个非常重要的开发纪律：**代码进入主分支之前必须由真实环境验证，而不是依赖开发者或 AI 对“应该能运行”的判断。**

对于未来涉及学生身份、权限、报告发布等高风险功能，这种门槛会直接降低上线后出现基础错误、迁移失败或环境不一致的概率。

### 带来的好处

1. **把错误提前到开发阶段**：依赖版本问题在任何业务数据进入系统之前就被发现。
2. **证明 PostgreSQL 路线真实可运行**：不是只写在架构文档里，CI 已实际启动 PostgreSQL 并完成 migration。
3. **建立可重复验收机制**：后续每个功能都可以复用同一套检查流程。
4. **避免“文档看起来正确”带来的假安全感**：这次官方文档与实际包仓库可安装版本出现时间差，CI 成为最终事实来源。
5. **减少长期维护债务**：GitHub Actions 已更新到当前 runtime，避免明知存在弃用警告仍继续累积。

### 当前遗留风险

1. **测试覆盖仍然极小**：目前只证明工程可启动和健康检查可访问，还不能代表未来业务逻辑正确。
2. **依赖没有 lock file**：当前使用受控版本区间，便于获取安全补丁，但不同时间安装可能得到不同 patch 版本；进入生产前需要决定正式锁定策略。
3. **CI 只覆盖单一 Python / PostgreSQL 组合**：当前选择 Python 3.13 + PostgreSQL 17，足够作为主开发基线，但未来升级仍需专门验证。
4. **CI 通过不等于生产就绪**：安全、备份、并发、监控、恢复等仍未完成。

### 下一步

Phase 1 已达到进入下一阶段的条件。合并本分支后，进入 Phase 2：`School / Tenant` 模型与多学校数据隔离基础。
