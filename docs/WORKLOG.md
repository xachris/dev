# 开发日志 / Worklog

本日志记录每个开发阶段不仅“做了什么”，还必须记录它对学校业务可能产生的影响、带来的收益以及仍然存在的风险。

每次完成一个可独立验收的开发段落后更新本文件。

---

## 2026-09-16 — Phase 1A：Django 工程底座

### 做了什么

- 建立 `feat/phase-01-foundation` 开发分支。
- 以 Django 5.2 LTS 为核心建立后端工程。
- 采用 PostgreSQL 作为标准数据库。
- 建立 Development / Test / Staging / Production 四套配置入口。
- 默认语言设为简体中文，默认时区设为 `Asia/Shanghai`。
- 建立 `core / schools / accounts / students / academics / reports / events / notifications / audit` 模块边界，但暂不提前实现业务模型。
- 增加中文首页、基础错误页和 `/health/` 健康检查。
- 增加最小自动化测试和 GitHub Actions 检查流程。
- 因仓库此前没有 CI，先将测试工作流引导文件加入 `main`，再由本分支重新触发 Pull Request 检查。
- 开发环境继续禁止任何真实学生数据。

### 对业务可能产生的影响

本阶段不会直接改变教师、学生或家长的工作流程，它的价值是建立后续所有业务功能共同依赖的稳定底座。

最重要的业务意义是：以后学习报告、请假、考勤、作业等能力不需要各自重复建设账号、权限、配置、日志和部署结构，避免平台从一开始就形成彼此割裂的“小系统”。

### 带来的好处

1. **降低未来改造成本**：环境和模块边界先统一，后续功能可以在同一工程规范下自然扩展。
2. **降低上线风险**：测试、预发布、生产配置从第一天分离，减少“开发环境能跑，生产环境混乱”的概率。
3. **减少供应商锁定**：Django + PostgreSQL + Linux 路线可迁移，不依赖单一云平台。
4. **中国场景默认正确**：中文和上海时区不是后期补丁，而是基础默认值。
5. **尽早形成质量门槛**：每次 Pull Request 可自动进行 Django 检查、数据库迁移和测试。
6. **为多学校扩展留出空间**：`schools` 等核心模块已经建立边界，但没有提前引入复杂多租户基础设施。

### 当前遗留风险

1. **CI 结果仍需完成验证**：测试工作流已经就位，本分支需要等待并读取首次托管执行结果；首次失败应视为正常工程反馈而不是绕过。
2. **数据库尚未建立业务模型**：当前 PostgreSQL 只承担 Django 基础表，School / Student 等将在下一阶段建立。
3. **生产安全仅有最低骨架**：HTTPS 终止、反向代理、安全头完整配置、密钥管理、备份和监控仍属于后续阶段。
4. **健康检查目前是浅检查**：`/health/` 只证明 Web 应用能响应，还没有检查数据库等依赖状态。
5. **依赖仍需持续安全更新**：Django 采用 5.2 LTS 分支并允许安全补丁升级，但后续仍需建立依赖升级机制。
6. **尚未证明模块边界完全正确**：这些边界是基于当前产品哲学设计的起点，后续应根据真实业务闭环验证，而不是为了保持目录漂亮而拒绝必要调整。
