# 开发双重核验标准

本项目每个可独立合并的开发阶段必须同时通过两类核验：**功能核验**与**业务意义核验**。

只有“代码能运行”不足以证明功能值得存在；只有“业务想法听起来不错”也不足以进入主分支。

## 1. 功能核验（Functional Verification）

最低要求：

- Django system check 通过；
- migration 与模型定义无漂移；
- 数据库 migration 可从零执行；
- 自动化测试通过；
- 关键唯一性、隔离性、状态和权限约束有负向测试；
- 不使用真实学生数据作为开发 fixture；
- 新功能不会破坏已完成的核心流程。

对于涉及权限、身份和数据隔离的功能，必须重点测试“应该失败的请求真的失败”，而不是只测试成功路径。

## 2. 业务意义核验（Business Value Verification）

每轮开发必须回答：

1. 这个功能解决哪一个真实学校业务问题？
2. 它让哪个角色少做了什么重复或机械工作？
3. 它是否让系统能够自动推导原本需要人工再次录入的信息？
4. 新增的字段 / 表 / 状态具体由谁消费？如果暂时无人消费，为什么现在必须存在？
5. 是否出现“同一事实在两个地方重复保存”的情况？如有，为什么无法避免？
6. 这个设计是否提高了准确性、可追踪性、自动化程度或用户完成任务的速度？
7. 它为哪个下一阶段真实工作流提供了必要基础？
8. 如果删除本轮新增内容，未来具体哪个业务闭环会无法成立？
9. 本轮是否引入了比业务收益更大的长期维护成本？
10. 是否留下可能导致隐私泄露、跨学校越权、错误自动化或数据无法解释的风险？

## 3. 核验结论

每轮开发日志和 Pull Request 都要明确给出：

- **功能核验：PASS / PASS WITH RISK / FAIL**
- **业务意义核验：PASS / PASS WITH RISK / FAIL**

合并规则：

- 任一项为 `FAIL`：不得合并；
- 功能为 `PASS WITH RISK`：只有风险已经明确、不会破坏当前业务闭环，并有后续处理阶段时才允许合并；
- 业务意义为 `PASS WITH RISK`：必须说明为什么现在仍然值得开发，以及风险如何被限制；
- 两项均为 `PASS`：可以进入正常合并流程。

## 4. 业务核验不是“功能数量核验”

项目不以新增多少模型、字段、页面、API 或配置项作为进度指标。

一个阶段如果最后决定“少建一张表、少收一个字段、少让老师点一次”，只要业务闭环因此更清楚、更可靠，就属于正确进展。

核心判断仍然是：

> **系统是否让学校少做无意义工作，并让正确的信息在正确的时间推动正确的行动。**
