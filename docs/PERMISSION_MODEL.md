# 权限模型

## 核心规则

**一个学生，一个稳定平台身份；在不同学校拥有各自稳定学号；多种身份，不同视图。**

学生档案本身保持稳定，不同登录身份根据学校、角色、关系、任课范围和内容可见级别访问不同部分。

平台内部 `Student.id` 使用稳定 UUID；学校日常使用 `StudentSchoolMembership.student_number`。平台内部 ID 不是访问凭证，也不能替代权限校验。

## 身份与角色来源

本平台刻意不把所有身份都复制成一张“角色表”。不同身份应由最接近真实业务事实的数据产生：

- **学生身份**：`Student.user_account + StudentSchoolMembership`
- **家长 / 监护人身份**：有效的 `GuardianRelationship`
- **教师身份**：学校范围内有效的 `RoleAssignment(TEACHER)`
- **学科教师的具体范围**：未来由 `TeachingAssignment` 决定
- **班主任的具体范围**：未来由 `HomeroomAssignment` 决定
- **学术管理员 / 学校系统管理员**：学校范围内对应的 `RoleAssignment`
- **平台超级管理员**：属于技术运维能力，不等同于学校业务角色

这样可以避免“同一个事实在 RoleAssignment、TeachingAssignment、GuardianProfile 等多个位置重复保存”，降低权限漂移。

一个真实成年人可以同时拥有多个业务身份，例如：

```text
同一个 UserAccount
├── School A / TEACHER
└── GuardianRelationship -> 自己孩子
```

不需要创建“教师账号”和“家长账号”两套凭证。

## 主要业务角色

- 学生（Student）
- 家长 / 监护人（Guardian）
- 学科教师（Subject Teacher，由教师角色 + 任课关系形成）
- 班主任（Homeroom Teacher，由教师角色 + 班主任关系形成）
- 学术管理员（Academic Admin）
- 学校系统管理员（System Admin）

## 内容可见级别

### 学生与家长可见 `STUDENT_GUARDIAN`

学生本人、已授权家长和有业务权限的教职工可见。

典型内容：
- 作业与任务信息
- 一般学习进展
- 优势与亮点
- 面向学生的下一步建议
- 普通学校通知

### 仅家长可见 `GUARDIAN_ONLY`

已授权家长和有业务权限的教职工可见，学生本人不可见。

典型内容：
- 教师给家长的留言
- 家长配合建议
- 部分行为问题
- 不适合直接向学生展示的部分学业问题

### 仅教职工可见 `STAFF_ONLY`

仅具有明确业务需要的授权教职工可见。

典型内容：
- 内部审核备注
- 工作流说明
- 升级处理记录
- 敏感内部运营信息

## 关系校验

仅有角色还不够，每次访问还必须检查上下文关系。

例如：

- 学生必须通过自己的 `UserAccount` 访问，并且在目标学校拥有有效成员关系。
- 家长必须与目标学校中的 `StudentSchoolMembership` 存在有效 `GuardianRelationship`。
- 学科教师必须同时拥有教师角色，并与目标班级 / 学科存在有效任课关系。
- 班主任必须同时拥有教师角色，并与目标学生所在班级存在有效班主任关系。
- 学术管理员应尽量按校区、学部、年级或职责范围限制访问，而不是默认全校可见。

## 家长访问模型

一名学生在一所学校可以绑定多个授权家长，每位家长拥有独立、可审计的登录身份。

```text
Student（平台稳定 UUID）
└── School A Membership / S000381
    ├── Student Account
    ├── Guardian A Account
    └── Guardian B Account
```

家长授权绑定的是“这名学生在这所学校中的成员关系”，而不是自动获得这名学生在其他学校中的资料。

## 跨学校身份规则

平台允许同一个 `Student` 拥有多所学校的成员关系，以支持教育集团、多校区或经授权的转学连续性。但这是高敏感能力，必须遵守以下规则：

1. **禁止根据姓名、邮箱、生日、相似文本或 AI 推断自动合并跨校学生身份。**
2. 不同学校导入学生时，默认不能因为“看起来像同一个人”就复用既有 `Student`。
3. 跨学校身份关联必须由明确、可审计、经过授权的业务流程完成。
4. 一所学校只能通过自己的 `StudentSchoolMembership` 访问学生数据，不得因为底层 UUID 相同自动获得其他学校记录。
5. 后续 Student Timeline 必须区分学校数据边界，不能把跨校记录默认拼接给任一学校用户。

在请求级权限体系完成前，本项目不得接入真实学生数据。

## 技术管理员与业务管理员的区别

`RoleAssignment.SYSTEM_ADMIN` 表示某所学校的系统管理业务角色；Django 的 `is_staff / is_superuser` 是平台技术运维能力。二者不得自动互相赋权。

系统管理员默认也不应因为“能维护系统”就获得查看所有教育敏感内容的权限。

## 安全原则

1. 默认拒绝，明确授权后才允许访问。
2. 所有权限检查必须在服务器端执行。
3. 前端隐藏按钮不等于权限控制。
4. 高权限操作必须写入审计日志。
5. 技术管理员权限不自动等于查看教育内容的权限。
6. 日常学校业务不应依赖直接访问数据库完成。
7. UUID 的不可猜测性不能被当作安全边界。
8. 未完成请求级学校隔离与关系权限检查前，不得处理真实学生数据。
