# 数据模型

## 设计原则

平台数据模型围绕稳定身份、真实业务关系和学校作用域设计，不以“传统 SIS 有哪些字段”为起点。

核心原则：

1. 姓名只是显示值，不作为关系主键。
2. 登录账号、学生业务身份、家长授权和工作人员角色彼此分离。
3. 同一个真实人应尽量只有一个 `UserAccount`，不同业务身份通过关系表达。
4. 学校内可见学号属于 `StudentSchoolMembership`；平台内部 `Student.id` 是稳定 UUID。
5. 不自动根据姓名、邮箱、生日或 AI 推断跨学校学生身份。
6. 没有明确业务消费者的字段不提前加入。
7. 数据库负责确定性的唯一性和关系约束，人类负责业务判断。
8. 有效状态尽量由上游真实状态推导，而不是要求管理员在多个模块重复开关。

> 产品界面使用中文名称；代码层继续使用英文模型名和字段名。

# 已实现核心实体

## 学校 `School`

表示平台中的学校 / Tenant。

主要字段：`id`、稳定唯一 `code`、`name`、`status`、`language_code`、`timezone`。

已有业务关联数据时使用 `PROTECT`，优先归档，不直接级联删除历史。

## 学年 `AcademicYear`

属于某一所学校，包含 `name / starts_on / ends_on / is_active`。

约束：同一学校学年名称唯一；结束日期必须晚于开始日期。

## 用户账号 `UserAccount`

表示一个可认证的真实操作身份，基于 Django `AbstractUser`，使用 UUID 主键。

账号不是“学生账号 / 家长账号 / 教师账号”三套独立体系。同一个账号可以同时拥有多个业务身份，例如教师兼家长。

最终登录方式尚未冻结，未来可扩展学校代码 + 学号、邮箱、SSO 等方式，而不改变业务实体主键。

## 学校角色授权 `RoleAssignment`

只记录需要显式授予的学校工作人员基础角色：

- `TEACHER`
- `ACADEMIC_ADMIN`
- `SYSTEM_ADMIN`

不重复保存学生身份、家长身份、学科教师具体任课范围或班主任具体范围。

## 学生 `Student`

平台层面的稳定学生身份。

主要字段：`id`（UUID）、可为空的 `user_account`、`full_name`、时间戳。

当前不保存出生日期、性别、国籍等首个业务闭环尚未消费的资料。

## 学生学校关系 `StudentSchoolMembership`

表示一名学生在一所学校中的稳定成员身份。

主要字段：`school`、`student`、学校内部 `student_number`、`status`。

同一学生在同一学校只存在一条成员关系；同一学校学号唯一；不同学校可使用相同格式学号。

## 家长学生关系 `GuardianRelationship`

表示某一个用户账号被某所学校授权为某名学生的家长 / 监护人。

关系绑定 `StudentSchoolMembership`，不是只绑定全局 `Student`，因此 A 校的家长授权不会自动扩散到 B 校。

# 已实现学术结构

## 班级 / 教学分组 `ClassGroup`

属于一个 `AcademicYear`，并明确区分：

- `HOMEROOM`：行政 / 班主任班级，用于班主任管理和完整报告审核；
- `TEACHING`：数学分层、语言组、选修组等实际教学组织。

同一学年中分组名称唯一。

之所以不把两类组织混成一个“班级”，是因为它们在权限和工作流中的消费者不同。

## 学科 `Subject`

属于某所学校，包含稳定 `code` 和 `name`。

- 同一学校 `code` 唯一；
- 写入时自动去空格并转大写，避免 `CS / cs` 形成重复学科。

## 学生班级关系 `StudentClassMembership`

连接 `StudentSchoolMembership` 与 `ClassGroup`。

规则：

- 学生学校关系与分组必须属于同一学校；
- 在读学生同一学年最多一个有效 `HOMEROOM`；
- 可以同时属于多个 `TEACHING` 组；
- `.active()` 同时检查关系本身状态和学生是否仍在读，因此学生离校后不需要管理员再逐个关闭班级关系。

## 任课关系 `TeachingAssignment`

连接：

- `RoleAssignment(TEACHER)`
- `ClassGroup`
- `Subject`

用途：后续直接决定教师可以为哪些学生、哪门学科创建学习评价。

规则：

- 必须使用教师角色；
- 教师角色、学科、班级必须属于同一学校；
- 支持多名教师共同教授同一组同一学科；
- `.active()` 同时检查关系、教师角色与登录账号状态。

因此停用教师角色或账号后，不需要再到每一门课程手动关闭权限。

## 班主任关系 `HomeroomAssignment`

连接教师角色与 `HOMEROOM` 类型分组。

用途：后续决定谁可以查看、组织和审核完整学生报告。

当前允许共同班主任，但最终报告审批是“任一人可批、主班主任可批还是多人共同批”将在报告工作流阶段明确，而不在组织结构层提前猜测。

# 后续报告实体

以下仍属于后续阶段设计，字段将在真正开发时根据业务闭环再次核验，不视为已经冻结。

## 报告周期 `ReportCycle`

用于定义某个学年中的评价与发布时间窗口。

## 学科评价 `SubjectComment`

预计至少区分：学生可见反馈、家长专属信息、教职工内部备注和工作流状态。

## 学生整体报告 `StudentReport`

用于组合一个报告周期内的学科评价、审核状态与最终发布状态。

## 审核动作 `ReviewAction`

记录退回、批准、升级等业务动作。

## 通知 `Notification`

通知是 Outbox 记录，不是正式报告本体。正式报告留在学校系统内，外部渠道只负责通知。

## 审计事件 `AuditEvent`

用于记录权限变更、关系变更、报告发布和高权限操作等安全相关事实。

# 当前关键业务规则

1. 一个真实人尽量一个登录账号，多种业务身份通过关系表达。
2. 一个 `Student` 使用稳定平台 UUID；学校使用自己的稳定 `student_number`。
3. 跨校 Student 身份不得自动匹配或 AI 推断。
4. 家长授权必须是学校范围内的明确关系。
5. 教师角色不等于任课权限，学生访问范围必须由 `TeachingAssignment / HomeroomAssignment` 决定。
6. 行政班与教学分组是不同业务概念，不能因为 UI 方便就合并真相。
7. 邮箱、姓名、显示名称都不是学生或家长关系主键。
8. AI 不得创建、修改或覆盖学生—家长关系、跨校身份关系或权限授权。
9. “发布报告”是一种业务状态变更，不等于“发送邮件”。
10. 正式环境个人信息字段必须有明确消费者、访问范围、留存和审计规则。
11. `full_clean()` 不是最终安全边界；未来批量导入必须走统一 service / policy 层。
12. 请求级学校隔离和 Phase 5 权限系统完成前，不接入真实学生数据。
