# Phase 3 开发日志：统一身份与关系模型

日期：2026-09-16

## 1. 做了什么

本阶段建立了平台第一版统一身份与学校关系底座：

- `UserAccount`：平台登录身份，采用 UUID 主键；登录身份与学生、家长、教师等业务身份分离。
- `Student`：平台层面的稳定学生身份，采用 UUID；学生可以暂时没有登录账号。
- `StudentSchoolMembership`：学生与学校的稳定成员关系，保存学校内部学号与在读状态。
- `GuardianRelationship`：家长 / 监护人授权直接绑定某所学校中的学生成员关系，而不是只绑定全局 Student。
- `RoleAssignment`：只保存需要显式授予的学校工作人员角色，目前包括教师、学术管理员、学校系统管理员。
- 自定义 `AUTH_USER_MODEL`，为后续统一登录和多身份账号打基础。
- 增加 Django Admin 基础管理入口。
- 增加身份、学校作用域、唯一性、删除保护、家长授权范围等自动化测试。
- 新增 `docs/VERIFICATION_STANDARD.md`，正式规定以后每轮开发必须同时进行功能核验与业务意义核验。
- 更新权限模型，明确学生、家长、教师角色来自不同的真实业务关系，而不是把所有身份重复塞进一张角色表。
- 明确跨学校学生身份规则：禁止根据姓名、邮箱、生日、相似文本或 AI 自动合并学生身份。

### 刻意没有开发的内容

本阶段没有机械照旧计划创建 `GuardianProfile` 和 `StaffProfile`。

原因：目前这两张表没有独立、被业务消费的数据字段。家长身份已经可以由 `UserAccount + GuardianRelationship` 完整表达；工作人员身份可以由 `UserAccount + RoleAssignment` 表达。

现在先创建空 Profile 表，只会产生重复身份真相和未来同步负担，违反 `No Dead Data` 原则。

同样，本阶段没有把 `SUBJECT_TEACHER` 和 `HOMEROOM_TEACHER` 当作长期角色值保存。教师基础身份只记录为 `TEACHER`；具体“教哪个班哪门课”“是不是某班班主任”将在后续 `TeachingAssignment / HomeroomAssignment` 中表达。

## 2. 对业务可能产生的影响

这一阶段开始真正解决学校系统最基础但最容易被传统系统做复杂的问题：**一个真实的人到底需要几个账号，以及系统如何知道他和某名学生、某所学校之间是什么关系。**

核心业务影响包括：

1. 同一个成年人可以同时是教师和家长，但只使用一个平台账号，不需要维护两套密码、邮箱和个人资料。
2. 学生身份与登录账号分离，因此低龄学生即使没有登录需求，也可以先拥有完整、稳定的学生记录。
3. 学生在不同学校可以拥有不同校内学号，但平台层身份保持稳定，为教育集团、多校区或经过授权的转学连续性保留空间。
4. 家长权限绑定的是“学生在某所学校中的成员关系”，因此家长不会因为与 Student 存在关系，就天然获得该学生在其他学校的数据。
5. 教师角色和具体任课关系分离，为后续做到“教师只能评价自己真正教的学生”提供必要基础。

这一阶段本身仍不会直接减少老师填写报告的点击次数，但它减少了后续所有业务模块需要重复建设、重复维护身份和权限关系的工作。

## 3. 带来的好处

1. **减少重复账号**：一个真实人只需要一个平台登录身份，可以叠加多个业务关系。
2. **减少重复数据**：没有为家长、员工提前复制一套姓名、邮箱等资料。
3. **降低权限漂移风险**：学生身份、家长授权、教师任课关系分别由最接近真实业务事实的数据表达。
4. **支持未登录学生**：学生数据不依赖先创建账号，符合真实学校场景。
5. **支持多学校扩展**：同一个平台可以表达不同学校的学号和成员状态，而不是把学号当成全平台唯一自然键。
6. **为后续报告权限提供直接基础**：未来家长查看报告、教师填写评价、班主任审核，都可以通过现有关系继续收窄权限。
7. **避免过度建模**：没有为了“模型看起来齐全”创建暂时无人消费的 Profile 表。
8. **把复杂现实提前纳入正常模型**：家长兼教师、学生转校、多校集团等情况不需要以后靠特殊字段补丁处理。

## 4. 遗留风险

### 4.1 平台级 Student 属于高敏感设计

`Student` 是平台级稳定身份，可以拥有多个学校成员关系。这个设计有扩展价值，但也意味着跨学校身份关联必须非常谨慎。

当前风险：如果未来错误地根据姓名、邮箱、生日或 AI 相似度自动合并 Student，可能造成跨学校数据泄漏或错误身份合并。

当前控制：

- 已在权限规范中明确禁止自动跨校合并；
- 学校日常业务使用 `StudentSchoolMembership`，不直接把平台 UUID 当作学校访问范围；
- 当前系统没有真实学生数据、没有面向用户的学生查询接口；
- 请求级权限完成前不得接入真实数据。

### 4.2 请求级权限尚未完成

目前 `Student.objects.for_school()`、`RoleAssignment.objects.for_school()` 等只是数据层查询工具。开发者如果直接使用 `.objects.all()`，仍然可以在代码层拿到多学校记录。

真正的“用户只能访问自己学校”必须在后续权限阶段通过服务端统一策略强制执行。

### 4.3 `UserAccount.username` 目前仍是全平台唯一技术登录名

这可以保证账号唯一，但目前还没有决定最终登录体验，例如：

- 学校代码 + 学号；
- 邮箱；
- 手机号；
- 学校统一身份认证；
- 其他登录别名。

本阶段没有提前绑定某一种登录方式，避免未来学校接 SSO 时重构身份主键。

### 4.4 角色状态历史仍依赖未来审计层

`RoleAssignment` 和成员关系当前通过状态字段表达生命周期；重复创建被数据库阻止。以后角色被停用、恢复时的完整变化历史，需要 Phase 12 Audit Log 负责记录。

### 4.5 技术管理员与学校业务管理员容易被混淆

Django 的 `is_staff / is_superuser` 与 `RoleAssignment.SYSTEM_ADMIN` 是两类不同权限。后续界面和运维流程必须继续保持隔离，不能因为“系统管理员”这个名字相同就互相自动授权。

## 6. 业务意义核验

逐项检查：

1. **解决真实问题**：解决多角色人员重复账号、学生是否必须先有登录、家长权限如何绑定学校、教师角色如何与具体任课范围解耦。
2. **减少人工重复**：未来无需分别维护“家长账号”和“教师账号”的同一人资料。
3. **减少重复真相**：没有把学生 / 家长身份再重复写进 RoleAssignment；没有提前创建空 Profile 表。
4. **新增数据有明确消费者**：StudentSchoolMembership 将直接用于后续班级、任课、报告权限；GuardianRelationship 将直接用于家长报告访问；RoleAssignment 将用于教师和管理员基础授权。
5. **支撑下一阶段**：没有这层身份和学校关系，后续无法可靠回答“教师可以评价谁”“家长可以看谁”“班主任可以审核谁”。
6. **长期扩展性**：保留多学校、多角色、无学生账号、家长兼员工、转学等现实场景，不需要先写死单校单角色假设。

### 业务意义核验结论

**PASS WITH RISK**

理由：业务价值明确，而且是后续报告闭环不可缺少的底座；但平台级 Student 的跨学校身份能力天然具有较高隐私风险，请求级权限也尚未完成。

允许继续开发的前提：

- 当前只使用虚拟数据；
- 不提供真实学校用户访问；
- 下一阶段继续建立学术关系，随后必须在 RBAC + Contextual Permission 阶段把学校作用域和关系权限做成服务端强制规则；
- 在这之前不得进行真实学生生产试点。

## 7. 是否进入下一阶段

**允许进入 Phase 4：最小学术结构。**

理由：Phase 3 的功能基础已经稳定，业务意义成立，剩余风险已被清晰限定，而且 Phase 4/5 正是降低这些风险所需要的下一步。

下一阶段重点不是增加更多学生字段，而是建立真正被报告工作流消费的：

- `ClassGroup`
- `Subject`
- `StudentClassMembership`
- `TeachingAssignment`
- `HomeroomAssignment`

每一个字段仍需回答“它具体服务哪个权限判断或工作流”，否则不添加。
