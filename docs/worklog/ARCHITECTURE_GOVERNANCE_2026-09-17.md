# 架构稳定性治理与前端决策固化（2026-09-17）

## 1. 做了什么

为了避免后续 AI 模型、开发者或供应商在不了解历史背景的情况下随意推翻已经验证过的技术路线，本轮新增并固化了架构决策机制：

- 新增 `docs/decisions/README.md`，建立 Architecture Decision Records（ADR）索引与变更规则；
- 新增 `docs/decisions/ADR-001-frontend-strategy.md`，正式记录当前前端默认使用 Django Templates + CSS + 少量 JavaScript，以及暂不全面迁移 React / Next.js 的原因；
- 新增根目录 `AGENTS.md`，作为后续 AI / 开发者接手须知；
- 更新 `README.md`，把 ADR 和接手规则放到项目入口；
- 更新 `docs/ARCHITECTURE.md`，把 ADR 纳入正式架构治理，并加入 Complexity on demand 原则。

## 2. 对业务的可能影响

这轮没有新增面向教师、学生或家长的业务功能，但它降低了一个长期且现实的组织风险：

> 不同模型、开发者或供应商因为个人偏好反复更换架构，导致已经验证的业务流程不断被重写。

对于希望服务多所学校、长期迭代的产品，这类“架构漂移”会直接增加：

- 开发周期；
- 回归风险；
- 培训和交接成本；
- 运维复杂度；
- 权限与安全退化概率；
- 已经投入但不能产生新业务价值的重写工作。

因此，本轮虽然不增加页面功能，但能够保护后续业务开发的连续性。

## 3. 带来的收益

### 3.1 让技术决策有上下文

以后看到“为什么不是 React”时，不需要重新猜测或重新争论，可以直接看到当时的产品阶段、现有代码资产、验证结果和成本收益判断。

### 3.2 避免框架偏好覆盖业务目标

明确规定：

- “更现代”；
- “更流行”；
- “模型更熟悉”；
- “行业常见”

都不能单独成为推翻已验证架构的理由。

任何变化必须回答真实业务问题和可衡量收益。

### 3.3 保留未来演进空间

ADR-001 并没有永久禁止 React。

它明确列出重新评估条件，例如：

- 整班类电子表格连续编辑；
- 复杂拖拽排课；
- 高频实时局部更新；
- 多客户端共享 API；
- 当前 Template 页面已经成为可测量的效率瓶颈。

因此架构稳定，但不是僵化。

### 3.4 对 AI 接手更友好

`AGENTS.md` 让未来编码代理在进入代码前就能知道：

- 应先读什么；
- 哪些原则不能轻率修改；
- 如何推翻旧 ADR；
- 每轮必须做功能核验和业务意义核验；
- 每轮必须更新工作日志。

## 4. 遗留风险

### 4.1 文档不能替代执行纪律

未来模型仍可能忽略文档，因此代码 Review、PR 检查和人工判断仍然重要。

### 4.2 ADR 可能过时

如果真实产品形态发生明显变化，但团队因为“已经有 ADR”而拒绝重新评估，也会形成另一种僵化。

因此 ADR 必须允许被新的、证据更充分的 ADR 替代。

### 4.3 当前没有自动检查“架构变更必须附 ADR”

目前这还是开发纪律，而不是 CI 强制规则。未来如果团队扩大，可以考虑 PR 模板或检查规则要求重大架构变化引用 ADR。

## 5. 功能核验结论

**PASS**

本轮是文档和治理变更，不改变运行代码。关键入口文件和架构文档已经建立相互引用，后续接手者可以从仓库根目录找到完整决策链。

## 6. 业务意义核验结论

**PASS**

虽然没有直接增加功能，但它明确降低长期重写、架构漂移和交接失真的风险，并保护当前已验证学习报告闭环不被无理由推倒重来。

## 7. 下一步

继续现有 Pilot 路线，不因为前端框架讨论中断上线验证：

1. 完成 Railway Pilot 部署；
2. 确认健康检查与登录；
3. 使用虚拟账号进行真人浏览器测试；
4. 收集教师连续录入、点击次数、完成时间等真实数据；
5. 只有当真实数据证明现有 UI 成为瓶颈时，再按 ADR-001 评估前端增强或架构演进。
