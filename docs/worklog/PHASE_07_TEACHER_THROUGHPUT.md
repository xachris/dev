# Phase 7 开发日志：教师高吞吐录入

日期：2026-09-17

## 1. 做了什么

本阶段把教师端从“逐个学生打开单独页面”升级为面向几十到上百名学生的班级 / 学科级工作区。

新增：

- 教学组 / 学科 / 报告周期级连续录入入口；
- 同一个页面切换学生，不再每人返回 Dashboard；
- 键盘优先交互：Tab 字段流、最后字段 Tab 自动保存草稿并进入下一位；
- Ctrl / Cmd + Enter 提交当前评价并自动进入下一位；
- 学生花名册侧栏、完成进度、退回状态；
- Excel / CSV 花名册模板下载；
- Excel / CSV 上传预检；
- 预检通过后人工确认，确认时再次核验当前权限 / 状态；
- 整批数据库事务写入，任意一行失败时整批回滚；
- Pilot 演示数据从 1 名学生扩展到 18 名纯虚拟学生；
- Academic Admin 的演示重置改为覆盖整个 18 人花名册，支持反复测试连续录入；
- 新增 ADR-002，固定连续录入 / 表格导入 / 自然语言 / 语音输入必须汇入同一 Policy / Service 的原则。

单学生评价页面保留，但降级为精准查看 / 异常修改入口，不再作为大量学生录入主路径。

## 2. 对业务的影响

原教师主流程近似：

```text
找学生
→ 打开页面
→ 填写
→ 保存 / 提交
→ 返回工作台
→ 再找下一个学生
→ 重复 N 次
```

现在变为：

```text
进入一次教学组工作区
→ 连续输入
→ 保存 / 提交
→ 系统定位下一名学生
→ 重复输入本身
```

因此教师工作量开始从“学生人数 × 页面导航成本”向“实际需要表达的信息量”靠近。

## 3. 带来的好处

### 3.1 连续工作流

教师不需要在 100 名学生之间反复执行页面导航和查找动作。

### 3.2 键盘成为一级交互

对熟练教师，鼠标不再是每名学生都必须使用的工具：

- Tab：字段间移动；
- 最后字段 Tab：保存草稿并移动下一位；
- Ctrl / Cmd + Enter：提交并移动下一位。

### 3.3 批量导入不绕过业务规则

Excel / CSV 不是“直接写数据库”的管理员后门。它仍然经过：

- 当前教师真实任课关系；
- 当前教学组；
- 报告周期；
- `can_edit_report_subject()`；
- `save_subject_comment()`；
- `submit_subject_comment()`。

### 3.4 批量身份匹配更安全

系统只以学校范围内稳定学号作为导入匹配键。

姓名只做交叉校验。如果 A004 在文件里写成另一名学生姓名，预检会阻止导入，而不是“相信 Excel”。

### 3.5 原子导入

确认导入时再次验证当前状态，并在一个数据库事务中完成整批写入。

避免出现前 63 人成功、第 64 人失败、剩下 36 人不知道处于什么状态的半成品导入。

### 3.6 Pilot 可反复测试

演示重置现在会清空整个 18 人班级的学科评价和报告状态，而不是只重置最初的 A001。这样连续录入、批量导入和状态推进可以反复从同一个干净起点验证。

## 5. 业务意义核验

### 已验证

1. 录入的主单位已经从“单个学生页面”提升为“教学组任务”；
2. 页面导航不再与学生人数线性增长；
3. Excel / CSV 可以成为批量输入方式，而不是复制出一套新业务系统；
4. 所有输入仍共享学生身份、权限和报告状态机；
5. 教师可以在同一页面看到完成进度和退回异常；
6. Pilot 可以整班重置，支持产品负责人反复比较交互方案。

### 仍需真人验证

自动化测试无法判断：

- 最后字段 Tab 自动保存 + 下一位是否符合教师肌肉记忆；
- Ctrl / Cmd + Enter 是否是最自然的“提交并下一位”；
- 18–30 人后侧边花名册的信息密度是否合适；
- 100 人规模时是否需要搜索、状态筛选和“只看未完成”；
- 三个评价字段是否应该同时常驻，还是按教师习惯折叠低频字段；
- 教师是否更偏好连续卡片模式、类 Excel 模式，或两种模式共存。

### 业务意义核验结论

**PASS WITH HUMAN UX VALIDATION REQUIRED**

原因：架构和流程已经实质减少无意义导航，但“是否足够流畅”必须通过真实人的连续填写体验判断。

## 6. AI 语音 / 自然语言需求

已正式确认并写入 `ADR-002-teacher-input-channels.md`，但本阶段不假装已经完成语音能力。

目标链路为：

```text
Audio
→ Speech-to-Text
→ Transcript
→ AI Semantic Extraction
→ Structured Draft
→ Student Identity Resolution
→ Human Confirmation
→ Existing Report Service
```

必须遵守：

- AI 输出是候选草稿，不是授权事实；
- 学号可稳定匹配；
- 只有姓名时必须在当前任课范围内解析；
- 同名 / 模糊 / 低置信度不得自动落库；
- AI 不能绕过 Policy；
- 真实数据阶段不默认长期保存原始录音；
- STT / AI Provider 必须可替换，不绑定核心报告模型。

## 7. 遗留风险

1. 当前连续页会把整个教学组的评价表单渲染到 DOM；100 人通常仍可接受，但应通过浏览器性能和真实操作验证；
2. Tab 在最后字段自动保存并跳转属于高效率但较强的交互，需要防止教师误触；
3. 当前批量预检数据暂存在用户 Session，适合数百行级别，不应演变成大规模数据导入平台；
4. Excel / CSV 可以提高效率，也会让教师一次性引入大量错误文本，因此必须继续保持预检而不能提供“跳过检查”；
5. 语音 / AI Provider 尚未落地，不能把 ADR 当成已完成能力；
6. 当前 Pilot 仍全部使用虚拟数据，不能因为批量功能可用就提前导入真实学生资料。

## 8. 是否允许进入线上 Pilot

**已允许并已上线 Staging Pilot。**

代码功能核验达到 PASS，线上容器也已验证 migration、静态文件、18 人 seed 和健康检查。下一步的关键任务是由产品负责人实际连续填写一组学生，记录：

- 完成一名学生需要多少动作；
- 是否出现不必要的鼠标移动；
- Tab / 快捷键是否自然；
- 是否需要“只看未完成 / 搜索学生 / 跳过当前学生”等功能；
- 批量模板是否符合真实教师已有 Excel 工作方式。
