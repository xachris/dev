# Pilot UI 开发日志：图形化学习报告闭环与线上 Staging 准备

日期：2026-09-17

> 本轮是 Phase 7–9 的**可测试 Pilot 切片**，不是宣布教师批量录入、班主任异常处理、学生/家长 Portal 三个阶段已经全部完成。

## 1. 做了什么

把 Phase 6 已验证的报告状态机接到真实浏览器页面，形成可以登录、点击、填写、审核、发布和查看的最小图形系统。

本轮新增：

- 登录 / 退出；
- 角色化工作台；
- 学科教师评价编辑页；
- 班主任审核页；
- Academic Admin 发布动作；
- 学生 / 家长已发布报告视图；
- System Admin 无教育内容默认视图；
- 纯虚拟 Pilot 数据生成命令 `seed_demo`；
- Academic Admin 一键重置演示报告；
- Railway / 通用 PaaS 所需的 `DATABASE_URL`、Gunicorn、WhiteNoise、`Procfile`、启动脚本；
- production settings 下的静态文件与演示初始化 CI 核验；
- 浏览器级角色与权限测试。

Pilot 仍坚持 Django Templates + 普通 HTML/CSS，不引入 React / Node / SPA。

## 2. 对业务的影响

这是项目第一次从“后端模型正确”进入“真实角色可以完成事情”。

完整可测试链路为：

```text
CS 教师填写并提交
→ 数学教师填写并提交
→ 系统自动识别报告完整
→ 班主任审核 / 可只退回一门
→ 班主任批准
→ Academic Admin 发布
→ 学生查看学生反馈
→ 家长查看学生反馈 + 家长专属信息
```

同时系统管理员登录后不会因为技术管理员身份自动看到学生教育内容。

## 3. 带来的好处

### 3.1 后端权限第一次经过真实页面消费

权限不再只是测试函数存在，而是 View、表单和模板真正依赖 Policy / Service 层。

### 3.2 教师只输入一次

同一份 `SubjectComment` 从教师填写一直被班主任审核、学生 / 家长查看，没有要求任何角色再抄写一份相同事实。

### 3.3 正常状态继续自动推进

最后一门必需学科提交后，报告自动进入班主任审核；班主任不需要点击“开始审核”。

### 3.4 可重复真实测试

Pilot 数据全部为虚拟数据；`seed_demo` 幂等，重复部署不会不断生成重复学生和重复报告。

Academic Admin 还可以重置演示工作流，方便反复测试完整链路。

### 3.5 部署形态保持可迁移

应用使用标准 `DATABASE_URL + Gunicorn + WhiteNoise + start.sh`，没有把核心运行方式绑定到某个云厂商专用 SDK。

## 4. 业务意义核验中发现并修正的问题

### 4.1 班主任提前看到教师草稿

第一版班主任页面直接遍历 `SubjectComment`，虽然写权限正确，但页面可能显示教师尚未提交的 DRAFT 内容。

这违背 Phase 6 已确定的规则：

> 教师草稿属于教师工作区；班主任只在提交后进入审核视图。

已修正为所有班主任内容都经过 `subject_comment_content_for()`；草稿只显示“尚未提交”，不暴露文本。

并新增浏览器级负向测试锁死该规则。

### 4.2 演示重置越权请求表现不够严格

第一版普通教师调用重置动作时，Service 会拒绝，但 View 把它作为普通业务错误后重定向。

已改为在 View 入口先验证 Academic Admin 权限；越权请求直接返回 HTTP 403。

## 5. 功能核验

最终 GitHub Actions 最新 HEAD 已验证：

- Django system check：PASS；
- migration drift：PASS，`No changes detected`；
- PostgreSQL 从零 migration：PASS；
- production `collectstatic`：PASS；
- production `seed_demo` 连续执行两次：PASS，第二次复用同一份报告；
- 自动化测试：**110 / 110 PASS**。

浏览器级测试至少覆盖：

- 未登录不能进入工作台；
- 教师只能看到自己真实任课学科；
- 教师不能直接打开其他学科；
- 班主任不能读取教师草稿；
- System Admin 默认看不到教育内容；
- 两门课提交后自动进入审核；
- 班主任批准；
- 单学科退回 + 重提；
- Academic Admin 发布；
- 学生看不到 guardian / staff 字段；
- 家长看得到 guardian 字段但看不到 staff 字段；
- 未发布报告学生 / 家长不可打开；
- 演示重置只有 Academic Admin 可执行。

### 功能核验结论

**PASS**

## 6. 业务意义核验

本轮证明了：

- 同一份学习事实可以跨教师、班主任、发布者、学生、家长自然流转；
- 权限关系会真实影响浏览器页面，而不是依赖前端“隐藏按钮”；
- 系统能够让用户围绕待办和状态完成事情，而不是要求用户维护第二份数据；
- 图形层没有迫使我们引入额外前端技术复杂度。

但本轮还**没有证明大班级教师录入效率已经达到目标**。当前演示只有 1 名学生、2 门学科，仍缺少：

- 一个页面连续处理整个班；
- 自动保存草稿；
- 大批量学生状态扫描；
- 真人教师完成时间 / 点击次数测量。

### 业务意义核验结论

**PASS WITH RISK**

## 7. 遗留风险

1. Pilot 仅有 1 名虚拟学生和 2 门学科，不能代表 20–30 人班级录入效率；
2. 当前草稿是显式“保存草稿”，尚未实现自动保存；
3. Event / Student Timeline / Audit / Notification Outbox 尚未接入；
4. 线上 Pilot 可以公开演示账号，因为数据完全虚拟；任何未来含真实数据的环境必须取消公开账号 / 共用密码；
5. Railway 只是 Staging 验证载体，不代表未来中国大陆正式部署选型；
6. 真实数据试点前仍需备份恢复、安全审计、访问日志、运营流程等验证。

## 8. 是否允许进入线上 Pilot

**允许。**

理由：核心业务、对象级权限、生产配置、静态文件和虚拟数据初始化均已通过自动核验；当前数据完全虚拟。

线上 Pilot 的目的仅是：

> 让真实人通过浏览器体验完整流程，并开始发现自动化测试无法判断的交互效率与业务问题。

这不是正式生产许可，也不是接入真实学生数据的许可。
