# Phase 4 开发日志：最小学术结构

日期：2026-09-16

## 1. 做了什么

本阶段只建立学习报告闭环真正需要的学术关系：

- `ClassGroup`：学年内的学生组织单元，并明确区分：
  - `HOMEROOM`：行政 / 班主任班级；
  - `TEACHING`：数学分层、语言分组、选课组等实际教学组。
- `Subject`：学校范围内的学科代码与名称。
- `StudentClassMembership`：把学生的学校成员身份连接到 HOMEROOM 或 TEACHING 组。
- `TeachingAssignment`：教师角色 + 学科 + 班级 / 教学组，作为未来“教师可以评价哪些学生”的事实来源。
- `HomeroomAssignment`：教师角色 + HOMEROOM，作为未来“谁可以审核完整学生报告”的事实来源。
- 所有核心学术关系都提供学校作用域查询。
- 增加跨学校关系阻止、角色类型校验、唯一性校验、共同授课、多教学组等测试。
- 学科代码写入时自动去空格并转大写，避免 `CS` / `cs` 成为两门重复学科。
- 将“有效关系”改为派生状态：
  - 学生班级关系只有在自身有效且学生仍处于 `ACTIVE` 学校成员状态时才实际有效；
  - 任课 / 班主任关系只有在关系本身、教师角色和用户账号均有效时才实际有效。

### 刻意没有加入的字段

没有加入：

- 年级编号；
- 教室；
- 课程节数；
- 排课时间；
- 学科颜色 / 图标；
- 部门；
- 课程难度；
- 教师工号；
- 大量课程元数据。

这些信息目前都不是学习报告权限闭环的必要条件。等未来排课、课程目录或 UI 真正消费时再增加，避免把学术结构提前变成传统 SIS 的字段仓库。

## 2. 对业务可能产生的影响

这一阶段第一次让系统能够从结构化事实回答学校里两个非常重要的问题：

1. **这位教师实际上教哪些学生、哪门学科？**
2. **这名学生的完整报告应该由哪一个班主任组织审核？**

这意味着未来教师进入报告页面时，不需要人工选择全校学生，也不需要管理员为每次报告重新维护一份名单。系统可以从 `TeachingAssignment + StudentClassMembership` 自动推导教师的学生范围。

同时，HOMEROOM 与 TEACHING 分开，使国际学校常见的数学分层、语言分组、选课班不会和行政班混成一团。学生不需要因为参加三个教学组而复制三份学生档案。

## 3. 带来的好处

1. **减少重复权限配置**：教师是否能评价某名学生未来由真实任课关系推导，不需要另建“报告权限名单”。
2. **减少重复学生数据**：一个学生可以属于一个行政班和多个教学组，仍然只有一个学生身份。
3. **班主任责任边界更明确**：HOMEROOM 单独建模，为完整报告审核提供明确组织边界。
4. **支持真实国际学校教学结构**：分层班、语言班、选修组和共同授课都可以表达，不必以后临时打补丁。
5. **正常状态自动推导**：学生离校、教师角色停用或账号停用后，相关关系自动从 `.active()` 结果中失效，不要求管理员去每个模块再关一次。
6. **减少脏数据**：学科代码自动规范化，降低重复学科造成的报告和统计分裂。
7. **跨学校关系更难误建**：学生、班级、教师角色和学科必须属于同一学校，正常写入路径会拒绝混校关系。
8. **没有为了“以后也许有用”堆字段**：当前数据结构仍紧贴首个学习报告闭环。

## 4. 遗留风险

### 4.1 模型校验不是最终安全边界

`save() -> full_clean()` 可以保护正常 ORM 和 Django Admin 写入，但 Django `bulk_create()`、部分批量 `update()`、Raw SQL 或数据库外部导入可以绕过 Python 层业务校验。

当前控制：

- 当前没有批量导入入口；
- 继续只使用虚拟数据；
- Phase 5 权限与后续导入服务必须通过统一 service / policy 层写入；
- 能下沉到数据库的唯一约束已经下沉，但跨表业务一致性仍需要应用服务控制。

### 4.2 离校后复学的旧班级关系可能重新生效

当前 `.active()` 会结合 `StudentSchoolMembership.status` 推导实际有效状态，因此学生离校后旧班级关系立即失效，不需要人工逐条关闭。

但如果未来将同一学校成员关系从 `WITHDRAWN` 直接恢复为 `ACTIVE`，旧的 `is_active=True` 班级关系也可能重新进入有效集合。

这不是当前虚拟数据阶段的阻塞问题，但正式“复学 / 重新入学”工作流必须明确：

- 是恢复旧组织关系；还是
- 在重新激活学生前先显式关闭旧关系并建立新关系。

不能让系统自行猜测。

### 4.3 班级关系目前没有独立生效日期区间

当前通过 `is_active + created_at / updated_at` 表达关系状态，足以支撑第一版报告权限。

如果未来需要精确回答“某学生在 2026 年 10 月 3 日属于哪个班”，或中途转班后重建历史课表，就需要引入明确的 `starts_on / ends_on` 或事件化历史，而不能滥用 `updated_at` 作为业务日期。

### 4.4 一个 HOMEROOM 可以有多个班主任

当前允许共同班主任，这是现实学校存在的场景。但未来报告审批必须明确：

- 任一班主任都可批准；
- 指定主班主任批准；或
- 多人共同批准。

Phase 4 只表达真实组织关系，不提前猜测审批制度。该问题必须在报告工作流阶段配置清楚。

### 4.5 批量导入与外部 SIS 同步尚未设计

未来若从 iSAMS、Excel 或其他 SIS 导入班级 / 任课关系，需要保证所有外部写入也经过同一套学校边界和业务约束，不能为“导入方便”绕开规则。

## 6. 业务意义核验

逐项检查：

1. **真实业务问题明确**：教师评价范围和班主任审核范围必须来自真实教学组织，而不是人工维护第二份权限名单。
2. **减少重复工作**：未来学科报告名单可从任课与学生分组自动生成。
3. **减少重复数据**：学生参加多个教学组不复制学生档案；“学科教师 / 班主任”也不重复存成静态角色。
4. **新增字段有消费者**：`group_type` 直接决定班主任审核边界；`TeachingAssignment` 直接决定学科评价权限；`HomeroomAssignment` 直接决定完整报告审核权限。
5. **提高准确性**：跨校关系、非教师任课和重复学科代码在写入阶段即被拦截。
6. **提高自动化**：有效状态由上游学生 / 教师状态共同推导，减少人工同步多个模块。
7. **没有提前膨胀成完整 SIS**：未增加首个业务闭环不使用的课表、教室、年级元数据等字段。

### 业务意义核验结论

**PASS WITH RISK**

业务价值明确，是 Phase 5 权限体系和后续学习报告闭环的必要基础；剩余风险主要集中在批量写入绕过校验、复学生命周期、历史生效区间和多人班主任审批政策。

这些风险当前均未暴露给真实用户，也不会阻塞继续构建权限层。

## 7. 是否进入下一阶段

**允许进入 Phase 5：RBAC + Contextual Permission。**

但 Phase 5 是真实数据上线前的重要安全门槛，必须重点验证“禁止访问”的路径，而不只是成功访问路径。

Phase 5 至少需要证明：

- A 校任何普通业务用户不能读取 B 校学生；
- 教师只能访问自己有效任课关系覆盖的学生；
- 班主任只能获得自己 HOMEROOM 学生的完整报告审核范围；
- 家长只能访问有效 GuardianRelationship 对应的学生；
- 学生只能访问自己的学生空间；
- 学术管理员和学校系统管理员权限边界明确；
- Django 技术超级管理员和学校业务管理员不是同一权限概念；
- 所有核心权限判断集中在服务端 policy 层，不靠页面隐藏按钮。
