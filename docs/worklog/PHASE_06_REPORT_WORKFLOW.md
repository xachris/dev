# Phase 6 开发日志：学习报告状态机与对象级权限

日期：2026-09-17

## 1. 做了什么

建立首个可运行的学习报告业务闭环核心：

- `ReportCycle`：报告周期；
- `StudentReport`：一名学生在一个周期中的工作流容器；
- `SubjectComment`：一个学科的一份唯一评价事实；
- `ReportAction`：退回、批准、发布等需要人工判断的动作记录；
- 服务层状态机：填写、提交、退回、重提、批准、发布；
- 对象级内容权限：学生、家长、学科教师、班主任、Academic Admin、System Admin 获得不同能力与字段视图；
- 报告学科快照：创建报告时根据当时真实任课关系自动生成学科工作槽，防止后续调课篡改历史报告结构。

## 2. 业务流程

第一版实际状态流收敛为：

```text
DRAFT
→ IN_REVIEW
→ APPROVED
→ PUBLISHED
```

异常修改路径：

```text
IN_REVIEW
→ RETURNED
→ 教师只修改被退回学科
→ IN_REVIEW
```

最后一门必需学科提交后，系统自动进入 `IN_REVIEW`，不额外要求班主任点击“开始审核”。

## 3. 业务收益

1. 学科教师只产生一次学习事实，后续审核和展示复用同一对象。
2. 班主任只退回有问题的学科，不要求整份报告重新填写。
3. 报告学科由系统自动生成，不要求管理员维护第二份“报告学科名单”。
4. 报告创建后学科构成被冻结，不受以后调课、换老师影响。
5. 发布与邮件彻底分离，邮件服务故障不会影响报告业务状态。
6. 学生只读取学生可见反馈；家长额外读取家长专属信息；`staff_note` 不向外暴露。
7. Academic Admin 可执行发布，但不会因此自动获得所有教育内容读取权。
8. System Admin 默认不获得教育内容读取权。

## 4. 关键设计修正

第一轮实现曾让“报告应有哪些学科”持续从实时任课关系推导。

功能测试虽然全部通过，但业务意义复核发现：如果报告创建后发生调课，历史报告结构可能被未来关系变化影响。

因此改为：

```text
创建 StudentReport
↓
读取当时真实教学关系
↓
系统自动创建 SubjectComment 工作槽
↓
这些工作槽成为该报告周期的学科快照
```

换老师时，新教师可以依据新的有效任课关系继续负责既有学科槽，但不会新增、删除旧报告中的学科构成。

## 5. 权限与内容边界

- 学科教师：只维护自己真实负责的报告学科；
- 班主任：只审核真实 HOMEROOM 范围学生；
- 学生 / 家长：发布前不可读取报告内容；
- 学生：发布后只看 `student_feedback`；
- 家长：发布后看 `student_feedback + guardian_message`；
- `staff_note`：仅具有明确业务职责的教职工读取；
- Academic Admin：发布能力不等于默认读取全部内容；
- System Admin：默认不读取教育内容。

## 7. 业务意义核验

核心问题：

> 教师是否只需产生一次学习事实，后续审核、发布、学生查看、家长查看即可继续消费，而不要求其他角色重复录入？

当前答案：**是。**

并且报告学科快照解决了实时任课关系对历史报告造成漂移的问题。

### 业务意义核验结论

**PASS WITH RISK**

遗留风险：

- 尚无真实浏览器 UI / endpoint；
- 自动保存、批量录入和操作效率尚未经过真人测试；
- 历史报告长期访问政策仍需后续明确；
- Event / Audit / Notification Outbox 尚未接入；
- 当前仍只允许虚拟测试数据。
