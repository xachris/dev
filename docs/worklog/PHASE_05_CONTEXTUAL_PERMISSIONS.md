# Phase 5 开发日志：RBAC + Contextual Permission

日期：2026-09-17

## 1. 做了什么

本阶段建立集中式服务器端 Policy 层，使权限由真实学校关系推导，而不是维护第二份人工权限名单。

新增：

- `visible_student_memberships_for(user, school)`
- `can_access_student_space(user, student_membership)`
- `writable_student_memberships_for_subject(user, school, subject)`
- `can_write_subject_comment(user, student_membership, subject)`
- `reviewable_student_memberships_for(user, school)`
- `can_review_student_report(user, student_membership)`
- `can_manage_academic_structure(user, school)`
- `can_manage_school_accounts(user, school)`

同时建立完整负向权限测试，覆盖：

- 跨学校访问；
- 非绑定家长；
- 非任课学生；
- 非任教学科；
- 非班主任审核；
- 停用家长关系；
- 停用任课关系；
- 停用班主任关系；
- 停用教师角色；
- 停用用户账号；
- 失效学年；
- 学生离校；
- 学校暂停；
- 学术管理员越权读取学生空间；
- 系统管理员越权读取学生空间；
- Django superuser 自动获得业务权限。

### 设计收敛

原计划曾考虑在 Phase 5 同时实现 `STUDENT_GUARDIAN / GUARDIAN_ONLY / STAFF_ONLY` 的完整内容级权限。

本轮业务核验后决定：**内容级权限延后到 Phase 6，与真实 `SubjectComment / StudentReport` 对象一起实现。**

原因是当前没有真实内容对象。如果现在设计一个泛化的“能否查看家长专属内容”函数，很容易把“教师对学生有某种关系”错误放大成“教师可以看该学生全部家长专属内容”。

因此 Phase 5 只回答关系和操作范围；Phase 6 再回答具体对象、具体字段的可见性。

## 2. 对业务可能产生的影响

这一阶段把学校权限从“配置型权限”转成“关系型权限”。

例如：

```text
教师能评价哪些学生
=
当前有效学年
+ 有效教师角色
+ 有效任课关系
+ 学生有效教学组关系
+ 学生仍在读
```

而不是每个报告周期再让管理员上传一份“教师—学生权限名单”。

家长权限同理：家长解绑后，学生空间访问自动消失；不需要再去报告模块、通知模块等地方逐个删除权限。

班主任调班、教师离职、学生离校、学校暂停等组织变化，也会通过真实上游关系改变权限结果。

## 3. 带来的好处

1. **减少重复维护**：不需要第二套“谁能看谁”的权限名单。
2. **减少权限漂移**：任课关系或家长关系改变后，权限自动跟随真实事实变化。
3. **跨学校边界更明确**：A 校关系不能产生 B 校权限。
4. **最小权限更强**：Academic Admin / System Admin 不因为“管理员”名称获得所有学生内容。
5. **技术权限与业务权限分开**：Django superuser 不自动进入学校业务授权。
6. **后续 UI/API 更安全**：可直接使用已经过滤好的 QuerySet，而不是查询全校学生后再依赖开发者手工过滤。
7. **为学习报告提供直接能力**：教师填写范围和班主任审核范围已经可以从真实结构自动计算。
8. **没有新增权限数据库表**：尽量复用真实业务关系，没有制造新的权限数据孤岛。

## 4. 遗留风险

### 4.1 Policy 存在不等于所有未来代码都会正确调用

当前集中 Policy 已建立，但 Phase 5 还没有真实业务 View / API。

后续如果开发者绕开 Policy，直接使用 `StudentSchoolMembership.objects.all()`，依然可能产生越权。

控制措施：

- 后续业务页面/API默认使用 Policy 提供的 QuerySet；
- 对每个真实 endpoint 增加 403 / 404 越权测试；
- Code Review 中把“是否经过 Policy”作为权限检查项。

### 4.2 内容级权限尚未实现

`can_access_student_space()` 只表示存在进入学生业务上下文的关系，不代表可以读取该学生所有报告字段。

Phase 6 必须针对：

- 学生可见反馈；
- 家长专属信息；
- 教职工内部备注；
- 创建者；
- 学科；
- 报告状态；
- 审核角色

建立对象级权限。

### 4.3 学术管理员当前没有细分校区 / 学部 / 年级范围

当前 `ACADEMIC_ADMIN` 的管理权限以学校为单位。

这是第一版最小实现。未来如果一所大型学校存在小学部、中学部、高中部或多校区，应增加明确 scope，而不是继续扩大“全校管理员”。

### 4.4 历史数据访问规则尚未冻结

当前教师权限只使用有效学年，以避免旧任课关系继续产生当前访问权。

但未来历史报告场景需要明确：

- 原任课教师是否仍可查看已经发布的历史报告；
- 教师离职后是否完全失去历史访问；
- 家长在学生离校后可以保留哪些历史资料。

这些应由报告对象生命周期和学校政策决定，不能由 Phase 5 猜测。

### 4.5 学校暂停后学校 System Admin 也失去运营权限

当前学校状态为 `SUSPENDED / ARCHIVED` 时，学校范围 Policy 默认拒绝。

这意味着恢复暂停学校需要平台级运维能力，而不是让暂停学校自己的 System Admin 自行恢复。

这是偏保守的安全选择，正式 SaaS 运营模型确定后需要再次核验。

### 4.6 技术超级管理员的物理能力仍然存在

业务 Policy 不给 Django superuser 学生业务权限，并不意味着数据库管理员在基础设施层物理上无法接触数据。

正式生产需要运维账号隔离、审计、最小化 superuser 使用和 break-glass 制度。

## 5. 功能核验

### 第一轮

建立初版 Policy 与负向权限矩阵后执行 GitHub Actions：

- Django check：通过；
- migration drift check：通过；
- PostgreSQL 从零 migrate：通过；
- 全部自动化测试：通过。

### 业务审查后的修改

第一轮通过后，没有直接合并，而是继续检查权限语义，发现：

1. `can_access_student()` 名称过宽，未来可能被误用为“可读取学生所有内容”；
2. 教师 / 班主任权限需要排除失效学年的旧关系。

因此：

- 改名为 `can_access_student_space()`；
- 文档明确其只是学生业务上下文权限；
- 教师与班主任 Policy 只使用有效学年；
- 补充失效学年、失效任课、失效班主任和跨校家长等负向测试。

### 第二轮

GitHub Actions 再次完整运行：

- Django check：通过；
- `makemigrations --check --dry-run`：通过；
- PostgreSQL migration：通过；
- 共运行 **62 个测试**：全部通过。

### 功能核验结论

**PASS**

权限层能够根据当前已建模的身份、关系、学校状态和学术关系稳定计算允许 / 拒绝范围。

## 6. 业务意义核验

核心问题：

> 如果学校增加第 801 名学生、教师离职、学生换班、家长解绑、学年切换，是否需要管理员再维护一份权限名单？

当前答案：**不需要。**

真实关系变化即可改变权限结果。

逐项核验：

1. 教师访问范围来自任课关系，而不是手工授权名单。
2. 班主任审核范围来自 HOMEROOM 关系。
3. 家长范围来自明确 GuardianRelationship。
4. 学生只进入自己的学生空间。
5. 管理员不会仅凭角色名称获得全部学生内容。
6. 技术 superuser 和学校业务角色不混淆。
7. 权限 QuerySet 可以直接作为后续页面/API安全数据入口。
8. 没有为了权限系统再建立一套重复的数据模型。

### 业务意义核验结论

**PASS WITH RISK**

核心业务价值成立，而且比传统“维护角色表 + 维护额外权限名单”的模式更接近学校真实组织。

风险主要在于：真实 View/API 尚未接入、内容级对象权限尚未完成、历史访问政策尚未冻结、Academic Admin 的细粒度 scope 尚未设计。

因此 Phase 5 可以进入下一阶段，但仍然不允许接入真实学生生产数据。

## 7. 是否进入下一阶段

**允许进入 Phase 6：报告数据模型、状态机和对象级内容权限。**

Phase 6 必须在同一个阶段同时验证：

- `SubjectComment` 三类内容字段的对象级可见性；
- 教师只能创建 / 修改自己有真实任课权限的学科评价；
- 班主任只能审核真实 HOMEROOM 范围；
- 学术管理员的发布 / 升级权限不能被理解成默认读取全部内容；
- 状态变化必须通过服务器端权限校验；
- 学生 / 家长 / 教职工对同一个报告对象得到不同字段视图。
