# 产品设计哲学

本文档定义“学校数字化平台”的核心设计哲学。它不是可选建议，而是后续产品、架构、数据模型、交互、自动化与 AI 功能设计时的默认约束。

## 1. 从第一性原理出发，而不是复制传统 SIS

系统设计不以“传统学校系统都有什么模块”为起点，而以“学校真正需要完成什么事情”为起点。

每一个功能都必须先回答：

1. 它解决了什么真实业务问题？
2. 谁因此少做了什么？
3. 哪些错误因此减少？
4. 哪些流程因此更快？
5. 哪些用户体验因此更好？

如果唯一答案只是“可以记录这项数据”，则默认不值得开发。

## 2. 系统不是记录系统，而是行动系统

传统系统常见模式：

```text
Form -> Database Row
```

本平台目标模式：

```text
Event -> State Change -> Automatic Action -> Human Intervention Only If Needed
```

数据必须推动状态变化、自动化、判断或后续行动。

## 3. 不产生“死数据”

项目采用 **No Dead Data** 原则。

任何新增字段、表、事件或日志，都应该至少回答：

- 谁产生它？
- 谁使用它？
- 它会触发什么？
- 它是否会进入后续分析、决策、自动化或用户体验？

如果数据只被写入、长期无人使用、也不触发任何动作，则应优先删除，而不是继续扩大采集范围。

## 4. 数据是流程自然留下的副产品

优秀系统不应该要求教师或行政人员为了“给数据库补数据”而额外工作。

数据应尽量在正常业务动作中自然产生。

例如：

- 家长提交请假 -> 自动形成请假事件
- 请假获批 -> 自动影响出勤预期
- 教师写学习反馈 -> 自动进入学习记录、周报、家长视图、学期总结素材
- 家长查看报告 -> 自动形成阅读事件

原则：**一次业务动作，同时形成可复用数据。**

## 5. 一份数据，只产生一次

系统不得要求用户重复输入已经存在的信息。

例如：

- 已批准请假，不应要求教师再次手动标记为请假
- 已有学生基本信息，不应在不同模块重复录入
- 教师已经连续记录学习反馈，学期末系统应能自动汇总，而不是要求教师重新从头总结

原则：**Single Input, Multiple Uses.**

## 6. 正常状态自动推导，人只处理异常

系统应最大限度自动处理确定性情况。

人工工作量应与异常数量成正比，而不是与学生数量成正比。

例如考勤：

错误模式：

```text
30 个学生 -> 教师逐个点击 30 次“到场”
```

目标模式：

```text
30 个学生
29 个状态可由课表、请假、设备或既有状态自动推导
1 个异常
-> 教师只处理 1 个异常
```

这是核心效率原则之一。

## 7. 让机器处理确定性，让人处理判断

机器负责：

- 匹配
- 聚合
- 检查
- 提醒
- 状态转换
- 重复检测
- 自动通知
- 结构化汇总

人负责：

- 教育判断
- 异常处理
- 审核
- 价值判断
- 复杂沟通
- 最终责任

系统不应把大量确定性点击留给人类。

## 8. 功能数量不是产品先进程度

本平台不以“模块数量”“字段数量”“配置项数量”作为产品成熟度指标。

真正指标包括：

- 教师操作时间是否减少
- 重复录入是否接近零
- 人工点击次数是否减少
- 流程等待时间是否缩短
- 错误率是否下降
- 自动处理比例是否提升
- 异常发现速度是否提高
- 家长完成任务时间是否降低
- 管理层人工协调是否减少
- IT 运维复杂度是否可控

任何新增功能都应明确它改善了哪些指标。

## 9. 业务结果优先于数据完整感

“系统里有这项数据”本身不是价值。

应优先问：

- 作业是否布置得更顺畅？
- 请假是否处理得更妥当？
- 考勤是否减少重复劳动？
- 课表是否减少人工干预？
- 学习报告是否生成、审核、发布得更高效？
- 家长是否更容易获得正确的信息？

如果业务没有改善，则数据采集本身不应被视为成功。

## 10. 避免模块割裂，围绕统一底层能力设计

系统不应把“考勤、请假、作业、报告、家长沟通”设计成彼此独立、互相不知道对方存在的孤岛。

底层应围绕更稳定的概念构建：

- Identity 身份
- Relationship 关系
- Event 事件
- State 状态
- Workflow 工作流
- Permission 权限
- Timeline 时间线
- Action 行动

上层功能是这些基础能力的组合，而不是每次重新造一套孤立系统。

## 11. 事件驱动，而不是表单驱动

重要业务动作应表达为事件。

示例：

```text
LeaveRequested
LeaveApproved
AttendanceExceptionDetected
AssignmentPublished
AssignmentSubmitted
TeacherFeedbackCreated
ReportApproved
ReportPublished
GuardianViewedReport
```

事件推动系统状态和后续自动化。

这样未来新增功能时，可以复用已有事件和状态，而不是继续“缝缝补补”。

## 12. 一个学生，一条持续成长时间线

Student ID 是稳定核心。

所有关键教育事件应尽可能落入统一学生时间线：

```text
Student Timeline
- 入学
- 班级变化
- 请假
- 出勤异常
- 作业
- 学习反馈
- 学习报告
- 家长查看
- 重要沟通
- 学期总结
```

不同页面只是对同一底层信息的不同视图，而不是各自维护一份互不相干的数据。

## 13. 一个学生，一个永久 ID，多种角色，不同视图

核心原则：

> **一个学生，一个永久 ID，多种角色，不同视图。**

学生、家长、教师、班主任、学术管理员、系统管理员访问的是同一个学校数据体系，但依据角色、关系和权限看到不同内容。

权限在服务端强制执行，不能依赖“把按钮藏起来”。

## 14. 报告留在学校系统内，外部只发送通知

核心原则：

> **报告留在学校系统内，通知可以发送到外部。**

正式学习报告、评价、敏感留言等应存储在学校控制的平台内。

邮件、短信、Push 等渠道只承担：

- 通知
- 验证码
- 必要提醒

而不是作为长期的学生数据存储介质。

## 15. AI 是能力层，不是系统依赖

AI 可以用于：

- 教师文字润色
- 汇总
- 异常检测
- 重复检查
- 长期趋势分析
- 辅助生成家长会摘要

但 AI 不得：

- 决定学生和家长身份关系
- 推断收件人
- 编造教育事实
- 绕过审核
- 成为核心流程唯一依赖

系统必须在 `AI_PROVIDER=none` 时仍然能正常运行。

## 16. 技术复杂度必须按需增加

默认采用最简单、可维护、可验证的实现。

原则：**Complexity on demand.**

只有当现实规模或功能确实要求时，才引入：

- Redis
- Worker
- 独立前端
- 微服务
- 消息队列
- Kubernetes
- 独立 AI 服务

禁止为了“架构看起来高级”而提前引入复杂度。

## 17. 模块化单体优先，保持巨大扩展空间

当前架构采用模块化单体，而不是过早微服务。

模块边界清晰，但共享统一身份、权限、事件和数据基础。

未来可在明确瓶颈出现后拆分服务，而不是第一天就承担分布式系统成本。

## 18. 面向多学校设计，而不是单校定制

平台定位为可复用的教育系统服务平台，而不是某一所学校的内部脚本。

从基础数据模型开始考虑多租户：

```text
Platform
  |- School A
  |- School B
  `- School C
```

每个学校可以有不同：

- 学年
- 年级结构
- 班级
- 课程
- 审批规则
- 报告模板
- 通知规则
- 品牌

但应共享同一套核心架构和产品哲学。

## 19. UI 不是装饰，UX 必须服务效率

后台系统不追求视觉炫技，但必须追求：

- 少点击
- 高信息密度
- 清晰状态
- 批量处理
- 自动保存
- 异常优先
- 手机端基本可用

教师和管理员界面优先级：

```text
效率 > 清晰 > 信息密度 > 美观
```

学生和家长界面优先级：

```text
清晰 > 简单 > 移动端体验 > 品牌一致性 > 美观
```

## 20. 软件上线后，组织应该更轻，而不是更重

引入软件以后，不应该为了“维护软件”持续增加大量数据录入和协调岗位。

目标趋势：

```text
Automation ↑
Repeated Entry ↓
Manual Reconciliation ↓
Administrative Work ↓
Business Quality ↑
```

如果一个系统上线后反而需要更多人专门“喂数据”“对账”“搬数据”，应视为架构或产品失败信号。

## 21. 每个新功能必须经过产品哲学检查

新增功能前必须回答：

1. 真实业务问题是什么？
2. 当前人工流程是什么？
3. 新功能能删除哪些人工动作？
4. 它是否重复已有数据？
5. 它产生的数据未来如何被使用？
6. 正常状态能否自动推导？
7. 人工是否只需要处理异常？
8. 是否可以复用现有 Identity / Event / State / Workflow / Permission？
9. 是否增加了不必要的长期维护成本？
10. 如何衡量业务结果是否真的改善？

如果这些问题无法回答清楚，应推迟开发。

## 22. 项目的长期判断标准

本平台不是为了成为“功能最多的学校系统”。

目标是成为：

> **更少录入、更少重复、更少等待、更少错误、更少人工协调，但能完成更多真实学校工作的现代学校运营平台。**

真正的产品价值不在于数据库里存了多少行，而在于系统让学校少做了多少无意义工作，并把多少原本割裂的流程变成自动、连续、可追踪的业务过程。
