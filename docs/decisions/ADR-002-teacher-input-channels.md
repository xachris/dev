# ADR-002：教师输入通道统一汇入同一业务写入层

状态：**Accepted**

日期：2026-09-17

## 背景

教师需要面对几十到上百名学生持续录入学习反馈。如果系统只提供“逐个学生打开页面”的单一输入方式，即使后端模型正确，教师端仍会因为页面切换、重复定位和机械操作产生大量无价值劳动。

当前确认需要三类高效输入通道：

1. **连续人工录入**：同一教学组内连续处理学生，键盘优先；
2. **Excel / CSV 批量导入**：适合教师已有表格或批量整理好的反馈；
3. **自然语言 / 语音输入**：教师可以口述学生与观察，AI 将其转换为结构化草稿。

这些输入方式解决的是“如何产生同一份学习事实”，而不是三套独立业务系统。

## 决策

所有教师输入通道必须最终汇入已经存在的报告领域 Service：

```text
连续录入 ─┐
Excel/CSV ─┼─> 权限校验 / 学生范围确认 -> save_subject_comment() -> submit_subject_comment()
自然语言 ─┤
语音 + AI ─┘
```

任何输入通道都不得：

- 直接绕过 Policy 修改 `SubjectComment`；
- 自己维护第二份“教师能处理哪些学生”的名单；
- 仅依靠前端隐藏按钮做权限控制；
- 使用学生姓名作为稳定唯一身份；
- 因为是 AI 生成内容就自动获得更高权限；
- 未经确认把低置信度姓名识别结果直接写入其他学生记录。

## 连续录入规则

- 主入口从“单学生页面”提升为“教学组 / 学科 / 报告周期”工作台；
- 当前学生完成后应能立即进入下一名学生，不要求返回 Dashboard；
- 键盘操作是一级交互：Tab 用于字段流，最后字段 Tab 可保存草稿并移动；Ctrl/Cmd+Enter 可提交并进入下一位；
- 单学生页面继续保留，作为精准查看与异常修改入口，而不是大规模录入主路径；
- 页面显示整体完成进度和退回异常，让老师优先处理未完成项。

## Excel / CSV 导入规则

批量导入必须采用“模板 / 上传 / 预检 / 确认”流程：

```text
下载当前任课花名册模板
→ 教师离线填写
→ 上传
→ 系统预检
→ 教师确认
→ 事务性写入
```

其中：

- 使用 `student_number` 作为学校范围内稳定匹配键；
- 姓名只用于交叉校验；
- 文件中学号重复必须拒绝；
- 不在当前任课范围内的学号必须拒绝；
- 已提交或已锁定评价不能被静默覆盖；
- 确认写入前必须再次检查当前权限和状态，避免预检后数据发生变化；
- 整批写入必须使用数据库事务，任意一行失败时整批回滚；
- 默认建议导入为 `DRAFT`，由教师抽查后提交；允许显式指定 `SUBMIT`，但必须满足提交校验。

## 自然语言 / 语音输入架构

语音能力拆为两个独立步骤：

```text
Audio
↓
Speech-to-Text Provider
↓
Transcript
↓
Semantic Extraction Provider
↓
Structured Draft
↓
Identity Resolution + Human Confirmation
↓
现有 Report Service
```

### Speech-to-Text Provider

只负责把声音转成文字。未来可以是：

- 本地 / 私有部署语音模型；
- 学校批准的云端语音服务；
- Pilot 阶段的测试 Provider。

核心业务不得依赖某一家模型供应商。

### Semantic Extraction Provider

只负责从自然语言中提取候选结构，例如：

```json
{
  "student_reference": "A023 / Mika",
  "student_feedback": "...",
  "guardian_message": "...",
  "staff_note": "...",
  "confidence": 0.96
}
```

AI 输出只是**候选草稿**，不是授权事实。

### 学生身份解析

身份解析遵循以下顺序：

1. 明确稳定学号并位于当前教师任课范围：可直接匹配；
2. 没有学号但姓名在当前范围内唯一精确匹配：形成候选，界面明确显示供教师确认；
3. 同名、模糊匹配或低置信度：不得自动写入，必须让教师选择；
4. 当前任课范围外的学生：即使 AI 识别出姓名，也不得写入。

### 音频与隐私

真实学校数据阶段默认原则：

- 不长期保存原始录音，除非有明确业务目的和保留政策；
- Transcript 和结构化草稿的保留周期应短于正式学习记录；
- 使用外部 AI / STT Provider 前必须明确数据区域、保留、训练使用和跨境规则；
- 本地 Provider 应可以替换外部 Provider，而不改变报告业务模型。

## 为什么不直接让 AI 写数据库

AI 最适合处理不确定性：语音识别、信息抽取、语言整理。

数据库写入、权限判断、学生身份和状态推进属于确定性业务规则，应由普通代码控制。

因此：

> **AI 可以提出“这句话可能属于 A023 的学生反馈”，但不能自行决定“把它写入 A023”。**

这与平台总体原则一致：机器处理确定性，人处理真正的不确定性；AI 不应把概率判断伪装成确定事实。

## 业务收益

- 同一份报告事实可以由不同高效方式产生，不制造重复数据模型；
- 教师可以根据工作习惯选择键盘、表格或口述；
- 新 AI Provider 不需要改动报告状态机和权限模型；
- 降低错学生、跨班、越权和批量覆盖风险；
- 后续可以客观比较各种输入方式的每百名学生耗时、点击量和纠错率。

## 风险

- 连续录入过度自动跳转可能造成教师误操作，需要明显保存 / 提交反馈和可逆草稿机制；
- Excel 仍可能包含错误内容，因此预检不能只检查文件格式，还必须核对业务范围；
- 语音姓名识别天然存在不确定性，不能用模型置信度替代身份确认；
- 外部语音 / AI Provider 可能产生隐私和跨境风险；
- 如果未来把 AI 输出直接自动提交，会破坏当前“人负责最终教育事实”的边界，应另立 ADR 重新评估。

## 重新评估条件

以下情况出现时，应新增 ADR 而不是静默改变本决定：

- AI 被授权自动提交正式评价而不经教师确认；
- 学校决定长期保存课堂 / 教师原始录音；
- 输入通道开始使用独立于主平台的学生身份体系；
- 批量导入被允许绕过现有 Policy / Service；
- AI 输入需要跨学校搜索或匹配学生。
