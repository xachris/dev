# ADR-001：前端架构策略——当前以 Django Templates 为默认，按业务证据再引入 React

- 状态：**Accepted / 已接受**
- 日期：2026-09-17
- 适用范围：School Platform Web UI、Pilot、后续学校运营后台与家长 / 学生 Portal
- 关联原则：`PRODUCT_PHILOSOPHY.md`、`ARCHITECTURE.md`、`DEVELOPMENT_PLAN.md`

## 1. 决策摘要

当前平台的默认前端路线为：

```text
Django
+ Django Templates
+ HTML / CSS
+ 少量 JavaScript
```

**当前不把 React / Next.js 作为默认前端，也不为了“技术现代化”重写已经通过业务与浏览器测试的 Django Template UI。**

这不是“永远禁止 React”。这是一个基于当前产品形态、现有代码资产、维护成本和业务验证结果作出的阶段性架构决定。

如果未来真实交互复杂度明显上升，可以重新评估 HTMX / Alpine.js / React / Next.js 等方案；但任何架构切换必须以真实业务收益为依据，而不是以前端框架流行度为依据。

---

## 2. 当时的项目状态

作出本决定时，平台已经完成：

- Django 5.2 LTS + PostgreSQL 工程底座；
- School / Tenant 多学校模型；
- 统一身份与关系模型；
- 学术结构；
- 服务端 RBAC + Contextual Permission；
- 学习报告对象级权限与状态机；
- 教师填写 → 提交 → 班主任审核 → 单学科退回 / 重提 → 批准 → 发布 → 学生 / 家长不同视图；
- 基于 Django Templates 的真实登录、Dashboard、教师页面、班主任审核页、Academic Admin 发布页、学生 Portal、家长 Portal；
- 浏览器级权限测试；
- Railway / 通用 PaaS 部署准备；
- Pilot UI 最新自动化核验为 110 个测试通过。

因此，当时面对的问题不是“项目尚无前端，应该从零选择 React 还是 Django Templates”，而是：

> 是否值得推翻一套已经接入真实 Policy / Service / Authentication / Workflow、并已经通过浏览器级测试的 UI 路线，再重新引入 React 前端？

答案是：**当前不值得。**

---

## 3. 为什么当前选择 Django Templates

### 3.1 当前学校业务的核心交互并不需要 SPA

当前首个业务闭环主要由以下交互构成：

- 登录；
- Dashboard；
- 表格 / 列表；
- 学生切换；
- 表单编辑；
- 提交；
- 审核；
- 退回；
- 批准；
- 发布；
- 不同角色读取不同字段。

这些交互的主要难点是：

- 权限正确；
- 状态正确；
- 操作次数少；
- 页面信息密度合理；
- 教师工作流高效；
- 数据不能丢；
- 跨学校和跨角色不能泄漏。

它们目前并不天然要求一个 React SPA。

### 3.2 当前优化目标是业务效率，不是前端框架先进感

平台真正要优化的是：

- 教师完成任务所需时间；
- 每名学生平均点击次数；
- 重复录入次数；
- 班主任人工检查量；
- 权限错误率；
- 数据丢失率；
- 家长获取报告的步骤；
- 系统长期维护成本。

如果切换到 React，却不能显著改善这些指标，那么这种切换没有足够业务价值。

### 3.3 当前 Django 链路已经完整且经过验证

当前已经形成：

```text
Model
↓
Policy
↓
Service
↓
View
↓
Django Template
↓
Browser
```

这一链路已经覆盖真实登录、权限、状态机和页面测试。

切换 React 意味着至少新增：

- REST / GraphQL API 层；
- API 身份认证策略；
- CSRF / Token / Session 协调；
- CORS；
- 前端状态管理；
- Node 构建链；
- 前后端接口契约；
- 额外 API 权限测试；
- 额外前端测试；
- 两套部署与故障边界（如果前后端分离部署）。

这些都不是免费复杂度。

### 3.4 单体 Web 架构降低安全和运维复杂度

当前同一个 Django 应用同时负责：

- Session；
- CSRF；
- 服务端 Policy；
- 业务 Service；
- HTML 渲染；
- 表单验证。

这使权限边界更容易集中控制，也减少了“前端隐藏了按钮但 API 仍然开放”之类的典型错误。

### 3.5 当前团队和产品阶段更需要可维护性

平台目标是能够被不同学校、不同未来开发者和不同 AI 模型长期维护。

减少独立技术栈数量意味着：

- 更少依赖；
- 更短部署链；
- 更少运行时；
- 更少版本冲突；
- 更少跨层调试；
- 更容易交接。

这与项目“Complexity on demand / 按需求引入复杂度”的原则一致。

---

## 4. 为什么这不是“Django Template 永远比 React 好”

本 ADR **不做以下结论**：

- React 不好；
- Next.js 不适合学校系统；
- Django Templates 永远足够；
- 系统以后不能前后端分离；
- 系统以后不能做独立 App。

本 ADR 只做一个更窄、更工程化的判断：

> 在当前业务复杂度和已经存在的代码资产下，继续 Django Templates 的边际收益高于立即切 React 的收益。

因此这是**当前最优路线**，不是宗教信条。

---

## 5. 什么情况下必须重新评估

出现以下一种或多种真实需求时，应重新评估前端方案：

1. **整班连续录入**需要接近电子表格的局部即时编辑，而整页刷新明显影响效率；
2. **30+ 学生批量编辑**需要大量本地状态、键盘导航、批量提交；
3. **复杂课表 / 排课**需要拖拽、冲突实时反馈、大量客户端交互；
4. **实时 Dashboard**需要高频局部刷新；
5. **复杂可视化或交互式数据探索**开始成为核心工作流；
6. **Web + Mobile App** 需要稳定共享 API；
7. 多个独立前端客户端需要消费同一业务能力；
8. Django Template + 少量 JS 已经导致明显的前端复杂度、重复脚本或难以维护的状态同步；
9. 真实 Pilot 数据证明现有页面无法达到既定业务效率指标，而现代客户端框架能够显著改善。

注意：

> “React 更流行”“2026 年应该用 React”“别人 SaaS 都用 React”不属于充分触发条件。

---

## 6. 优先升级路径

未来交互复杂度提升时，默认按以下顺序评估，而不是直接全部重写：

```text
Django Templates
    ↓
少量原生 JavaScript
    ↓
HTMX / Alpine.js 等局部增强（如果真实需要）
    ↓
局部 React island / 独立复杂页面（如果真实需要）
    ↓
完整 React / Next.js 前端（只有当产品形态已经证明值得）
```

这里的核心不是固定技术顺序，而是：

> **用最小新增复杂度解决已经存在的业务问题。**

---

## 7. 即使以后切 React，也不能推翻的业务边界

无论未来前端使用什么技术，以下原则保持不变：

- 权限由服务器端 Policy 决定；
- 前端隐藏按钮不等于权限控制；
- View / API 不能绕过 Service 直接随意修改核心状态；
- 多学校作用域必须继续在服务器端验证；
- 学生 / 家长 / 教师 / 班主任 / 管理员内容边界继续由服务器端决定；
- 学习事实保持单一来源，不因为前端技术变化复制第二份业务真相；
- UI 技术变化不得改变报告状态机语义；
- 新前端必须重新通过负向权限测试；
- 新前端必须证明业务效率至少不低于当前方案。

换句话说：

> React 可以替换展示层，但不能成为重写已经验证过的业务规则的借口。

---

## 8. 后续模型 / 开发者接手规则

任何未来 AI 模型、开发者或供应商在提出“切换 React / Next.js / 微前端 / SPA / 新 UI 技术栈”之前，必须先阅读本 ADR。

如果仍决定修改，应新增一个新的 ADR，例如：

```text
ADR-00X：前端架构从 Django Templates 演进至 React
```

新 ADR 至少必须回答：

1. 现有方案出现了什么**真实业务问题**？
2. 哪些可量化指标证明当前方案已经成为瓶颈？
3. 为什么局部增强不足以解决？
4. 新方案能带来什么具体业务收益？
5. 迁移需要重写哪些已经验证过的功能？
6. 会增加哪些依赖、运行时、接口和运维负担？
7. 权限、安全、状态机如何保持不退化？
8. 如何进行渐进迁移和回滚？
9. 新方案通过什么真实 Pilot 证明比旧方案更好？

**不得因为框架偏好、模型默认习惯或“现代化”标签直接推翻本决策。**

---

## 9. 决策结果

当前继续：

```text
Django + PostgreSQL + Django Templates + CSS + 少量 JavaScript
```

近期开发优先级：

1. 让线上 Pilot 可稳定访问；
2. 真人测试教师 / 班主任 / 学生 / 家长工作流；
3. 测量点击次数、完成时间和连续录入体验；
4. 根据真实阻力决定是否增加局部交互增强；
5. 在证据出现之前，不做全面 React 重写。

本 ADR 可以被未来的新 ADR 替代，但**不能被无记录地忽略或静默推翻**。
